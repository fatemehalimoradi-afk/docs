A bundle's logic decides who qualifies and what is discounted. The widget is how the offer looks and behaves on the storefront.

- **Bundles from a bundle type** use a built-in widget, changed from the form's **Style** panel and **Custom CSS**.
- **Bundle Engine bundles** have their own **JS code** (the renderer) and **CSS code**, under **Display options → Product detail page → Code**. The AI writes them; you can edit them.

These pages are the contract that code follows. Logic side: [how the pieces connect](/bundle-concepts).

## What you can extend

The renderer (**JS code**) and **CSS code** are per bundle. [Plugin hooks](/plugin-hooks) and [resolver stages](/resolver-stages) are global, loaded from any storefront script.

## How the page boots

```
app embed / app block renders a mount element   [data-nameless-block]
        │
        ├─ bundle data for this page is published to the runtime
        ├─ CSS code fetched once → injected as a scoped <style>
        └─ JS code loaded once via <script src> → your script calls
                 window.nameless.defineRenderer(fn, { viewVersion: 2 })
        │
runtime installs on window.nameless  (subscribe / dispatch / use)
        │
on every state change:  fn({ view, container, paint, locale, t, … })
        │
after every paint: the runtime's delegated listeners act on the
                   data-nameless-* attributes in your HTML
```

## The same widget everywhere

The same renderer and CSS run on your Shopify theme, in the admin **Preview**, in the [headless embed](/headless-bundles-api), and in [Tapcart](/tapcart). `ctx.locale` and prices follow each surface's language and currency. In the headless embed and Tapcart, `view.addToCart.themeButtonAdds` is always `false` and `view.subscriptions` is `null`.
