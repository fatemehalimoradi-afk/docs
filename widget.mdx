A Knit bundle is product sets, offers, conditions, rewards, **and** the widget. The logic decides who qualifies and what is discounted. The widget is how that offer looks and behaves on the storefront.

- **Bundles from a bundle type** use a built-in widget. You change it from the form's **Style** panel and **Custom CSS** — no code needed.
- **Bundle Engine bundles** have their own widget code: **JS code** (the renderer) and **CSS code**, under **Display options → Product detail page → Code**. The AI writes them; you can edit them. You don't need repository access.

The pages in this section are the contract that code follows. See [how the pieces connect](/bundle-concepts) for the logic side.

## What you can extend

| Extension point | What it is | Where it lives |
| --- | --- | --- |
| **Renderer function** | JavaScript that paints the widget HTML from the view | The bundle's **JS code** |
| **Styling** | CSS for the markup your renderer emits | The bundle's **CSS code** |
| **Plugin hooks** | JavaScript that observes, blocks, or annotates add-to-cart | Any storefront script you load |
| **Resolver stages** | JavaScript that reshapes the theme-button add-to-cart pipeline | Any storefront script you load |

The renderer and CSS are **per bundle**. Plugins and resolvers are **global** to the page and see every bundle on it.

The renderer draws, the engine decides. Prices, tier states, and what is missing all arrive already worked out in the [view](/renderer-view); the renderer computes none of it.

## How the page boots

```
app embed / app block renders a mount element   [data-nameless-block]
        │
        ├─ bundle data for this page is published to the runtime
        ├─ CSS code fetched once → injected as a scoped <style>
        └─ JS code loaded once via <script src> → your script calls
                 window.nameless.defineRenderer(fn, { viewVersion: 2 })
        │
runtime installs on window.nameless  (subscribe / dispatch / use)
        │
on every state change:  fn({ view, container, paint, locale, t, … })
        │
after every paint: the runtime's delegated listeners act on the
                   data-nameless-* attributes in your HTML
```

Two consequences:

1. **Your renderer runs many times** — on mount and after every quantity, variant, option, tier, or cart change. It rebuilds everything from the view each time.
2. **You never wire events.** The runtime owns all interactivity, discovered through data attributes. That is why the renderer can repaint on every call without breaking clicks.

## The same widget everywhere

The same renderer and CSS run on your Shopify theme, in the admin **Preview**, in the [headless embed](/headless-bundles-api), and in [Tapcart](/tapcart). `ctx.locale` and the view's prices follow each surface's language and currency. Two things differ off the theme:

- The headless embed and Tapcart always use the widget's own add-to-cart button, so `view.addToCart.themeButtonAdds` is `false` there.
- They sell one-time only, so `view.subscriptions` is `null`.

Code that follows the contract handles both without special cases.
